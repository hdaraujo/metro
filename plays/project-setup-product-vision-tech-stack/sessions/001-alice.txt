● I found where Horários Metrobus gets its timetable. It loads static JSON files from its own domain:

| File | Contents |
| --- | --- |
| `/data/stops.json` | 39 stops, each with id, code, name, lat/lng and the lines serving it |
| `/data/route-shapes.json` | map lines for S1, S2, U1, U2 and U3, one per direction ("Ida"/"Volta"), with colours |
| `/data/trips-{DU,Sab,Dom}.json` | every trip (weekdays: 452 trips), with line, direction, final destination and the time at each stop |

The files have open CORS, are cached for 5 minutes and were updated today. Three things to keep in mind:

- **They're undocumented and have no stated licence.** They're internal files of that app, so they could change without warning. We'd isolate them behind an adapter so a change in their format only breaks one module.
- **Trips refer to stops by name, not id.** We'll have to match them up.
- **There are only three day types: weekday, Saturday and Sunday.** Public holidays probably run the Sunday timetable, so we'll need a holiday calendar.

Here's the architecture I propose for the single `metro` repo:

- **Monorepo:** npm workspaces with `apps/api` (Node 24), `apps/web` (React + Vite PWA) and `packages/shared` (shared TypeScript types). TypeScript 7 everywhere, latest versions throughout.
- **API (the backend the web app talks to):**
  - Fetches and caches the Horários Metrobus JSON files through a *timetable source adapter*.
  - Works out each bus's estimated position by interpolating along the route shape between its scheduled stop times.
  - Calculates the "minutes away" figure for a given stop.
  - Serves the app one small JSON API.
  - Leaves room for an *Agit real-time adapter* later, which would take priority over estimates when it's live.
- **Web:**
  - Mobile-first and responsive on desktop, installable as a PWA.
  - Map built with MapLibre GL on OpenStreetMap tiles.
  - Uses browser geolocation to pick the nearest stop.
  - Refreshes bus positions every few seconds.
  - Always labels estimates as "scheduled."
- **Conventions:** ESLint + Prettier, Vitest for unit tests, Playwright for end-to-end tests, and one branch per play (as this repo already requires).

The biggest open point is where it runs, since that decides how the API is packaged and deployed.

- **`vision.md`**
  - A mobile-first web app showing your location, your nearest Metrobus stop, the buses on a map, and how many minutes each approaching bus is from that stop. You decide when to leave.
  - The main user is you; anyone else can use it anonymously.
  - Non-goals: Metrobus only, no accounts, no trip planning, no notifications.
  - I changed the "Real time" principle to match your decision: positions are estimated from the timetable and labelled "scheduled" until a live feed exists.
- **`tech.md`**
  - One `metro` repo with three workspaces: `apps/api` (Node 24), `apps/web` (React + Vite PWA with a MapLibre map) and `packages/shared`. TypeScript 7 and the latest versions throughout.
  - **Timetable data comes from Horários Metrobus** (its `stops`, `route-shapes` and `trips-{DU,Sab,Dom}` JSON files). These are undocumented and have no stated licence, so they sit behind an adapter.
  - Trips in those files refer to stops by name, and public holidays use the Sunday timetable.
  - **The Agit Planner real-time feed** is the planned next data source. It still returns 503 because Metro Mondego hasn't connected its data yet.
  - Every position and ETA says whether it is scheduled or live.
  - No database and no auth. Deployment is deferred, so the project is local-only for now.
  - Also defined: conventions (ESLint + Prettier, Vitest, Playwright), build/test/run commands, and a rule to keep serving the last good data, flagged as stale, if a source fails.
