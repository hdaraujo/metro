**What the play asks for:** a base app with scaffolding, a README, a `.gitignore` and the libraries installed. Its one feature is a map centred on the user's location, zoomed to show the nearest stop and, optionally, the nearest bus.

**How it fits:**
- **Vision:** it is the core of "opens straight onto a map showing where you are, your nearest Metrobus stop". It follows the Glanceable, Location-aware and Mobile-first principles and touches none of the non-goals.
- **Tech stack:** it follows the current `tech.md`, which now describes an app that runs entirely in the browser with no backend. This play needs no new technology, repository or goal.

**Notes for the Planner:**
- **The architecture changed after the last planning session.** That session assumed the old `apps/api` / `apps/web` / `packages/shared` layout, and it has been replaced by one npm package at the repo root with `src/sources/`, `src/domain/` and `src/ui/`. The browser fetches `stops.json` directly through an adapter in `src/sources/`, because the source allows cross-origin requests. There is no API or proxy.
- **Nearest stop:** the nearest-stop logic belongs in `src/domain/`, with Vitest unit tests.
- **Nearest bus:** showing it is optional in the intent. Including it brings the shapes and trips adapters, the interpolation logic and the "Scheduled" label into scope. The prototype already shows that label, but the Planner may prefer to leave the bus for a later play.
- **The new `tech.md` isn't committed yet.** It only exists as an uncommitted change on `main` in the main clone, so play branches cut from `HEAD` would still get the old backend version. It needs committing before DevOps creates this play's branch.

The vision and tech stack are ready, and the play can go to the Planner.
